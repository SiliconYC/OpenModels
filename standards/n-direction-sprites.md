# N 方向图生产规范（2D 精灵图管线）

状态：方案基线；虎式坦克为首个验证资产。本文约束未来实现，不表示 ControlNet 推理、16/32/64 方向图已经完成。目标分支：`dev`。

## 1. 目标及范围

通过「**统一正交三视图 → 仅用于空间约束的极简 3D → Python 批量正交渲染控制图 → AI 受控绘制 → 16/32/64 方向验证 → 透明 PNG 游戏素材**」，获得适合《突袭》类正交 RTS 的成熟商业级美术资源。3D 是生产夹具而非最终交付目标；不能用当前灰模外观要求最终 AI 画面同样粗糙。

这是 OpenModels 与「3D + UV + 贴图」**并行且相互独立**的第二条资产管线，不取代已有 3D 管线。两者共享有来源记录的三视图、工程尺寸、朝向约定；N 方向图不得以精细 3D、真正 UV、商业级 3D 贴图或 Issue #19 的完成作为前置条件。首轮只做炮塔/炮管/车体**一体版静态朝向**，暂不开发炮塔分体、炮管后坐、开火、制退器动画及履带运动。未来分体是独立技术验证，不能因一体版成功宣称分体版必然可行。

**首个样品**：1943 年早期 Tiger I，参考 Tiger 131；以 `models/vehicles/land/tiger-i/references/` 下现有三视图、`geometry.json` 和来源记录为起点。三视图中无法核实的炮塔不对称轮廓、轮系和炮口等，应修正或明确标注暂定，禁止混入晚期虎式特征。不得复刻版权不明的第三方蓝图/游戏精灵。

## 2. 技术事实与关键风险

- **控制图不等于 ControlNet 成功推理**：Python 渲染灰模只生成候选控制条件（轮廓、深度、分区遮罩等）。真正使用 ControlNet、多控制条件或其他受控生成算法，需要独立运行记录，注明模型/版本/参数、能力限制、服务端可用性和商业授权。
- **姿态控制不等于身份一致**：多次独立生成可能改变炮盾、轮组、编号、焊缝和磨损，不能凭单张漂亮图片宣称连续旋转成功。
- **4×4 拼图是批量审查/可选批量生成的工作单元**，不是规定 AI 每次必须在一张低解析度图片里完成最终 16 张。单张高分辨率受控重绘优先保证质量，最后再合成。
- **视觉质量与工程正确分开验收**：轮廓/视角/透明/方向索引合格不代表商业美术合格；所有自动检测不替代 360° 人工目视验收。

## 3. 目录与职责

每个资产可新增 `models/vehicles/land/<asset-id>/sprites/`，首例为 `models/vehicles/land/tiger-i/sprites/`：

- `spec.json`：方向角、正交相机、焦点/锚点、画布尺寸、版本、生成资源和方向索引；是所有步骤共用的唯一配置来源。
- `control/`：由可追溯几何实际渲染的逐方向轮廓、深度、部件 ID/分区遮罩、可选法线及 4×4 控制图；**不得把手画的视觉草图标为真实深度图**。
- `generated/`：AI 原始候选和生成元数据（提示词、负面词、种子、模型/控制网络版本、参数、参考源、服务商与授权）。
- `approved/`：明确验收通过、按方向编号的独立 RGBA PNG；原候选不因审核而消失。
- `export/`：发布的图集、逐方向 PNG、索引 JSON、统一锚点与可选独立接地阴影。
- `qa/`：逐方向差异报告、可重复测试和实际缩略图/360° 旋转录屏或帧序列证据。

跨资产通用代码放 `tools/sprites/`；通用验收放 `tests/`；实际静态在线浏览器验收在现有 `docs/` 中扩展**2D 方向图预览**，不得用 3D GLB 旋转冒充已生成的 PNG 方向图。不存在真实产物时不提前制造空目录。新增 `sprites/` 不改动既有 `source/`、`textures/`、`export/` 的 3D 语义；`asset.yaml` 可追加独立 sprites 状态与发布文件，不要覆盖 3D 状态。

## 4. 固定坐标、相机和帧索引

- **沿用既有工程坐标**：米制；车头 `+X`、向上 `+Y`、右侧 `+Z`；模型原点和炮塔枢轴沿用 `references/geometry.json`，偏差须记载。
- 只使用**真正 OrthographicCamera/正交投影**，不得用远距离透视或 AI 模拟正交冒充。相机俯角初测 35°（相对地平面），实际值在样张评估后冻结；固定方位、投影范围、分辨率、焦距意义上的正交尺寸、画面中心与地面锚点。同批文件禁止自动按各帧包围盒缩放、裁切、重新居中或动态运镜。
- 世界相机保持不动，只将**整车绕统一 Y 轴**转向；索引 `i=0…63`，角度 `theta_i = 360° × i / 64`，相对零位和 `+Y` 正向旋转。具体屏幕视觉顺/逆时针关系须在测试图/元数据证明，不凭语言猜测。最终图的 `heading` 与 `theta` 必须严格一致。
- 64 方向为共用角度格：首轮 16 方向取 `i=0,4,8,…,60`，升级 32 方向补充 `i=2,6,…,62`，升级 64 方向补齐剩下的奇数 `i`。已有验收帧不应重新随机生成。行优先 4×4 图集须提供明确的每格索引与相机/模型版本，避免错序。
- 首轮画布建议透明 `1024×1024` 单方向工作尺寸；4×4 的单格分辨率、拼图输出大小应配置化，不强迫一次 AI 生成 16 张低清画面。固定同一像素画布与投影尺度；固定地面投影锚点（例如模型原点），输出其 `pivot_px`，不得以各方向透明边界重新裁剪后丢失对齐。
- 使用规范 RGB/sRGB 与 straight alpha RGBA PNG；背景必须真实透明。接地阴影应可作为独立素材，不准把白底/棋盘底或带背景的效果图当透明 PNG。

## 5. 六步生产与阶段闸门

### A. 三视图与极简控制模型

审计既有三视图和 `geometry.json`，核对长宽高、炮塔轮廓、炮盾、炮管/炮口、履带外形、交错轮系可见轮廓。允许沿用旧灰模或 Issue #19 成果，但必须建立明确标识的「控制模型」版本：只增加对多个正交方向轮廓、遮挡、部件布局真正有帮助的几何；**不以精细 3D 完成度为目标**。保存生成脚本、GLB 与可复建说明。六个基本正交视角及若干斜向必须没有几何穿插/重大比例错位。

### B. 无 GUI 的 64 方向控制条件生成器

从冻结的控制模型和 `spec.json` 输出 64 套**同相机同构图**的实际可用参考图：

1. 外轮廓或边缘图（白/黑背景、是否含内部线须记录）。
2. 摄影机空间深度图（明确近远裁剪区间、量化方式、透明区域处理）。
3. 分区 ID 遮罩（车体、炮塔、炮管、履带/轮组等，稳定标签和颜色；可选法线图）。
4. 独立单方向图、4×4 索引拼图、manifest、校验值和叠图检查。

脚本必须确定性、可在无桌面软件的云端重建；可用现有 Three.js 正交相机配合无头 Chromium/WebGL 或 Python 的无 GUI 渲染器，实际选择以可复现、可靠读深度结果为准。不要使用仅绘制漂亮示意的假深度图。检查 0/360 连续性、方向步长、投影一致性、透明边界、像素锚点。

### C. 受控 AI 生成小样（正式 16 图前的强制门槛）

从间隔较大的典型方向选择至少四个（前、侧、后、斜），建议补到八个；同时输入：**三视图 + 同角度实际控制图 + 已接受的风格基准**。先确认模型是否实际支持对应的多条件控制及使用许可；保留原始候选、生成参数及失败样张。比较「只有提示词」「轮廓控制」「轮廓+深度/分区」的真实结果；不能把笼统的“严格按照 ControlNet”当工程验收。失败则回到控制模型或推理流程，不得直接扩展至 64 张。

### D. 16 方向基准图

以 `i=0,4,…,60` 生成 16 张正式方向；4×4 拼图统一检查并归档，逐方向 PNG 保留全画质。采用已接受基准图、必要的局部重绘或程序化投影补绘固定标识，确保装甲板、轮组、车长塔、炮盾、车身编号、徽章和主要污损位置跨角度连续。左右方向不能简单镜像带文字/不对称结构的图片。16 方向必须先完整 360° 实际播放并通过人工美术验收，才能进入下一阶段。

### E. 扩展至 32，再扩展至 64

优先使用**同一个锁定的控制模型、相机、风格规范、参考图版本**；新增帧以相邻已通过帧和其对应控制图作为约束，而非每帧重新凭空生成。依次补 `i=2,6,…,62` 和奇数 `i`，各阶段必须全周播放验收。应保存角色/车辆特征清单和跨角度错误台账；必要时失败帧局部重绘，不可通过重排编号、机械复制临近帧或插值冒充独立角度。**第一阶段到 64 即止**，不承诺 128/256 方向。

### F. 透明发布、2D 页面和独立审计

对每张通过验收的 PNG 做像素级 alpha 检验，统一锚点与画布；打包单张 PNG、可选精灵图集、帧索引和可复现导出程序。浏览器应直接播放真实 PNG（不是伪 3D），支持任意方向切换、循环、逐帧、16/32/64 档位切换及 64/128/256 像素实际 RTS 预览。审计真实透明背景、零位和末帧相接、编号/装甲细节一致、阴影分层、没有穿模漂移；给出**技术通过／不通过／未验证**与**商业美术通过／不通过／未验证**两项独立结论。

## 6. 验收证据及失败标准

每阶段至少记录：基础 `dev` SHA、输入文件 SHA、控制模型版本、`spec.json` 版本、生成/测试命令、生成模型及控制模块的标识和商业使用许可、代表性实物 PNG、脚本日志、自动测试结果、公开 Pages URL（若已上线）及实际人工检查清单。输出应当能追踪到源文件；既要有成功样本，也要保留典型失败案例。

自动检查建议涵盖：文件齐全/可解码、方向索引无重复与漏项、固定相机投影、画布尺寸/alpha 通道、统一 pivot、渲染轮廓重叠度、帧间轮廓/中心漂移、控制图与成图对齐、左右不对称标识。具体数值阈值须在试验样本上定标并写入代码，不能先编一个数字就宣称达标。外轮廓大错、炮管朝向错误、地面基线跳动、编号镜像/变化、履带轮组凭空增减、逐帧突然变化、显著 AI 涂抹感，均视为须修复问题。

**任何一步可失败并终止**。小样失败时不批准 16 图；16 图不合格不批准 32 图；32 图不合格不批准 64 图。不得将“已创建脚本/Issue”“自动测试全绿”“概念图漂亮”视为达成商业级方向图。

## 7. 实施与 Git 约束

沿用 `dev`、每 Issue 专属临时分支与 PR、细粒度提交/推送、最新提交完整验收、及时合并关闭、CI 并发去重；`main` 不得修改。可在 Agent 云端沙盒运行 Python 和无头 WebGL；**不要求用户 PC、Blender（包括后台）、Unity 或桌面 GUI**。若多视角模型推理必须使用外部服务，先证明接口真实可用、费用/额度可控且具备商业使用权限；不擅自上传受限参考素材，也不把 Github Actions 当大型生成式 AI 推理算力。

首轮交付范围仅限一体化 Tiger I 静态 N 方向图；炮塔/车体分离、炮口火焰、制退器/后坐、阴影物理以及游戏引擎集成应另立后续 Issue。
